## 一、产品定位

**一句话**：出发前把「每天去哪、几点到、待多久」排清楚，现场用地图看点位关系并一键跳导航，随手记账，旅行结束后有据可查。

**目标用户与真实痛点**

| 场景 | 痛点 | V1.0 的解法 |
|---|---|---|
| 自己出去玩，2–5 天 | 攻略收藏了一堆，到现场不知道先去哪 | 按天排点位 + 顺序调整 + 一键重排时间 |
| 到陌生城市 | 不知道几个点离多远、走回头路 | 地图页看当天点位分布，点开跳微信原生导航 |
| 花销记不住 | 回来算不清花了多少、花在哪 | 按行程记账，分类占比 + 每日分组 + 天数均摊 |
| 攻略信息不可靠 | 营业时间/预约/门票经常过期 | 硬事实统一标「待核实」，现场点一下才算已核实 |

**明确不做（V1.0）**：AI 助手、实时协同编辑、自动路径优化（TSP）、天气与客流、UGC 社区、机酒预订、多币种、PDF 导出。

## 二、版本规划

| 版本 | 范围 | 进入下一版的门槛 |
|---|---|---|
| **V1.0（已完成）** | 单人 + 云开发：行程多天/点位/时间/排序、地图只读点位 + 原生导航、单人记账、我的页统计、邀请占位 | 真机全流程走通、无阻塞缺陷 |
| **V1.5（功能已完成，待真机验收）** | 邀请码协同（含自行退出）、AA 分账与结算、行程编辑/复制、手帐照片、订阅消息（模板 id + 定时触发器） | 双人同时改与双人记账的真机验收；订阅消息实测一条真的到达 |
| **V2.0** | AI 助手（行程建议/行李清单/每日提醒）、路线顺序建议（近似解）、天气/人流接入、手帐成册导出 | AI 结果需入库复用；有真实用户量支撑成本 |

**为什么这么切**：实时协同和 LLM 生成都是「看起来简单、做起来无底」的功能，会让首版永远无法定稿。V1.0 先用单机闭环验证「用户愿不愿意把行程排进来」，这是后续所有功能的前提。

## 四、核心流程规则（已写进代码）

1. **新建行程**：结束日期 ≥ 开始日期，最多 15 天；`days` 一律由日期推导，用户不能手捏天数。详情页有「+ 加一天 / − 减一天」，减天仅在最后一天没有地点时出现，服务端也会校验被取消的天数里没有残留点位。
2. **加地点默认时间**：上一站开始时间 + 停留时长 + **30 分钟赶路缓冲**；当天第一站默认 09:00。
3. **按顺序重排时间**：以 09:00 起算，每站 = 停留 + 30 分钟，一键刷新整天时间。
4. **顺序调整**：上下移动本地先生效、再整体提交一次 `poi.reorder`，避免多次往返造成半成功。
5. **待核实**：手填的营业时间/预约/门票默认是「待核实」（来自攻略或别人口述）；点卡片信息区翻转成「已核实」，状态存库。
6. **地图只画有坐标的点**：没坐标就诚实提示「这天的地点都只有文字地址」，绝不猜位置。
7. **金额一律存「分」**，前端只负责展示 `¥12.50`；汇总在服务端算，明细与合计永远对得上。
8. **删除行程是软删除**：点位与账目一起标记 `deletedAt`，列表和记账里立刻看不到，数据保留给后续手帐回放；只有创建者能删。
9. **邀请**：创建者在详情页进「邀请同行」拿 6 位码（7 天有效）或直接转发；对方点卡片自动加入，或在「我的 → 加入同行的行程」输码加入。邀请码不复用、过期自动换新。
10. **角色**：创建者可删行程、可移除同行；同行可增删改点位与加减天数。非成员一律拒绝。
11. **并发用版本号乐观锁**：`trips.version` 每次内容写入 +1，写请求带上读到的版本，服务端用 `where({_id, version})` 做原子占位；版本不一致返回 `code:'conflict'`。客户端交互：点位类改动弹「仍然保存 / 刷新」，加减天与删行程只刷新提示（重试语义不明确）。
12. **AA 分账**：每笔记「谁付的钱」与「每人应摊」。默认对勾选成员均摊，除不尽的零头落在第一个人的份额里；也可以手改份额，但**合计必须等于金额**，客户端与服务端各校验一次。结算把实付与应摊相减，用贪心算法给出最少笔数的转账建议，只给建议不自动记账。
13. **行程编辑复用新建页**（`create?id=`）：预填原值，提交带 `version`；冲突时只重取版本号，不冲掉用户输入。改日期会整段重建 `days`，缩小天数时若后面几天还有地点会被服务端拦下。
14. **行程复制**：日期从今天重新起算、保持原天数，点位整份搬到新行程并按天重排 `order`，成员只留自己（复制后是一趟新的单人行程）。
15. **手帐照片**：`wx.chooseMedia` → `wx.cloud.uploadFile` 到 `journal/<tripId>/` → 写 `files` 记录；按 `dayIndex` 分组展示，单行程 ≤100 张。删除只软删记录，云存储原图保留，避免误删不可恢复。
16. **订阅消息**：必须用户点一下才能申请，一次授权只换一条推送（存 `trips.reminders`）。定时触发器每天 20:00 调 `sendDue`，只找「明天出发」的行程，用 `cloud.openapi.subscribeMessage.send` 发一条，发过就标 `sentAt` 不再重发。模板字段名集中在 `notify.js` 的 `FIELDS`，和公众平台不一致时只改那一处。
17. **退出行程**：同行可自己退出（`trip.leave`），退出后看不到这趟，之前加的地点和账目留给其他人；创建者不能退出，只能删行程。退出是成员变化、不碰内容，所以不校验版本号。
18. **账目编辑**：复用记账页（`add?expenseId=`），回填金额、付款人与各人份额；老数据只有 `splitWith` 时按人数均摊还原。
19. **预算与状态**：预算在详情页只显示数字，在账目页算「已花 / 剩余 / 是否超支」进度条；行程状态优先用手动标记的 `ended`，否则按日期推导（未出发 / 进行中 / 已结束）。

## 五、数据模型

> 设计原则：一切挂 `tripId`；`_id` 由客户端 uuid 生成（幂等）；`order` 进位到「天」；软删除 `deletedAt`；成员用数组，为 V1.5 协同预留。

集合共 5 个，首次请求由云函数自动创建：`trips` / `pois` / `expenses` / `files` / `users`。

### trips

| 字段 | 类型 | 说明 |
|---|---|---|
| `_id` | string | uuid |
| `ownerOpenid` | string | 创建者 |
| `memberOpenids` | string[] | 查询用：`where({ memberOpenids: openid })` 命中数组包含；V1.5 加人不改结构 |
| `members` | `[{openid, role, name, joinedAt}]` | `role`：`owner` / `editor`；前端不显示昵称，只显示 openid 后四位 |
| `version` | number | 乐观锁版本号，内容写入 +1；v1.0 老数据在首次读取时补 0 |
| `inviteCode` / `inviteExpireAt` | string / number | 6 位邀请码（去 I/O/0/1）与过期时间（7 天） |
| `title` / `destination` | string | 名称(≤20) / 目的地(≤30) |
| `startDate` / `endDate` | string | `YYYY-MM-DD` |
| `days` | `[{index, date}]` | 由日期推导，禁止手改 |
| `mode` | string | `solo` / `group`；有人加入或只剩创建者时由服务端切换 |
| `transport` | string[] | `drive` / `transit`，暂只用于展示 |
| `budgetCents` | number | 预算（分） |
| `poiCount` | number | 点位数，服务端维护 |
| `status` | string | `planning` / `ongoing` / `ended` |
| `reminders` | `[{openid, templateId, at}]` | 订阅消息授权记录；真正推送还需定时触发器 |
| `createdAt` / `updatedAt` / `deletedAt` | number / string | 软删除 |

### pois

| 字段 | 说明 |
|---|---|
| `_id` / `tripId` / `dayIndex` | 归属 |
| `name`(≤30) / `address`(≤60) | 名称与地址，选点后自动回填 |
| `location` | `{latitude, longitude}` 或 `null`；gcj02 |
| `category` | 景点 / 餐饮 / 住宿 / 交通 / 购物 / 其它 |
| `plannedTime` | `HH:mm` 计划到达时间 |
| `durationMin` | 30 / 60 / 90 / 120 / 180 |
| `facts` | `{open, reserve, fee}` 各 ≤40 字 |
| `factsPending` | true = 待核实 |
| `note` | 备注 ≤200 字 |
| `order` | `(dayIndex+1)*100000 + 序号*1000`，单字段排序即得「按天 + 按序」 |
| `createdBy` / `createdAt` / `updatedAt` / `deletedAt` | 审计与软删除 |

### expenses

| 字段 | 说明 |
|---|---|
| `tripId` / `amountCents` / `currency` | 金额存分，币种固定 CNY |
| `category` | 交通 / 餐饮 / 门票 / 住宿 / 购物 / 其它 |
| `paidBy` / `paidByName` | 谁垫的钱（`openid` + 展示名）；默认自己，可从行程成员里选 |
| `splitWith` | string[]，兼容旧数据：参与分摊的成员 |
| `splits` | `[{openid, amountCents}]`，每人应承担的份额；合计必须等于 `amountCents` |
| `spentAt` | `YYYY-MM-DD` |
| `note` | ≤100 字 |
| `createdBy` / `createdAt` / `updatedAt` / `deletedAt` | 审计与软删除 |

### users

`openid`、`nickname`、`defaultCurrency`、`createdAt`、`updatedAt`（首次调用 `user.me` 时自动建）。

### 索引建议（控制台补，数据量起来再建）

- `trips`：`memberOpenids + updatedAt`
- `pois`：`tripId + order`；`tripId + dayIndex + order`
- `expenses`：`tripId + spentAt`

### 集合权限

5 个集合全部设「仅管理端可读写」——前端不直连数据库，所有读写都过云函数。

### files（手帐照片，已启用）

| 字段 | 说明 |
|---|---|
| `_id` / `tripId` | 归属行程 |

### V1.5 预留集合（暂不创建）

- `ai_results`：`{ _id, tripId, kind:'packing'|'daily', payload, createdAt }`

（邀请码没有单独建 `invites` 集合：直接放在 `trips` 上，一次查询命中，少一张表；如需一人一码再拆。）

## 六、接口层

单个云函数 `api` + action 路由，前端统一封装在 `services/cloud.js`。

```
wx.cloud.callFunction({ name:'api', data:{ action, payload } })
→ 成功 { ok:true, data } ／ 失败 { ok:false, message, code? }（`code:'conflict'` 表示版本冲突）
```

| action | 作用 | 关键约束 |
|---|---|---|
| `user.me` | 当前用户 | 首次调用自动建 user |
| `trip.list` / `trip.get` | 我的行程、单个行程 | 只返回 `memberOpenids` 命中的 |
| `trip.create` / `trip.update` / `trip.remove` | 建 / 改 / 删 | 改日期重建 days；减天前校验孤儿点位；删除连带软删点位与账目；更新/删除带 `version`，删除限创建者 |
| `trip.invite` | 生成/复用邀请码 | 限创建者；未过期直接返回原码 |
| `trip.join` | 加入行程 | `tripId` 或 `code` 二选一；已是成员返回 `joined:false`；码过期拒绝 |
| `trip.removeMember` | 移除同行 | 限创建者；不能移除自己或创建者 |
| `trip.leave` | 同行自己退出 | 创建者不能退；同时清掉自己的订阅授权；不校验版本号 |
| `trip.copy` | 复制行程 | 日期从今天重算同天数；点位整份复制并重排 `order`；成员只留自己 |
| `poi.list` | 一次拿 trip + 全部点位 | 详情页 / 地图页 / 编辑页共用 |
| `poi.save` | 增 / 改点位 | 名称必填；一天最多 20 个；换天重排 order；带 `version` |
| `poi.remove` | 软删 | 同步回写 `trip.poiCount`；带 `version` |
| `poi.reorder` | 顺序 / 换天 / 重排时间一次提交 | 最多 300 条；带 `version` |
| `expense.list` | 明细 + 服务端汇总 | 分类占比在服务端算 |
| `expense.overview` | 我所有行程的花费聚合 | `aggregate + group`，不拉明细 |
| `expense.save` / `expense.remove` | 记账 / 改账 / 删账 | 金额必须 > 0；带 `_id` 即更新；`paidBy` 必须是成员，`splits` 合计必须等于金额 |
| `expense.settle` | AA 结算 | 实付/应摊/差额 + 贪心最少转账建议；老数据按 `splitWith` 均摊 |
| `photo.list` / `photo.add` / `photo.remove` | 手帐照片 | 限成员；单行程 ≤100 张；只软删记录 |
| `notify.subscribe` | 记录订阅授权 | 无模板 id 直接报错；一次授权只对应一条推送 |
| 定时触发 `dailyReminder` | 每天 20:00 发出发提醒 | 只发「明天出发」的行程；字段名见 `notify.js` 的 `FIELDS` |

**身份与鉴权**：`cloud.getWXContext().OPENID` 取身份，`guard.getTripForMember` 统一校验成员身份，越权直接抛错。前端永不信任、也不传递 openid。

**限额**：行程 ≤15 天、每天 ≤20 个点位、单次列表 ≤300 条、行程列表 ≤50 条、单行程照片 ≤100 张、单次选图 ≤9 张。

## 七、地图与定位方案

**已定方案（A 案）**：内嵌 `map` 只做点位展示，不做路线规划；导航交给 `wx.openLocation` 跳微信原生地图。

| 能力 | 实现 |
|---|---|
| 地图页 | 只画当天有坐标的点，marker 带序号 + 常显气泡，中心取点位均值；点标记弹卡片 → 跳原生导航 |
| 显示我的位置 | 用户点按钮才请求权限（`utils/location.js`：已授权直接用 / 未问过 `authorize` / 拒绝过弹「去设置」→ `openSetting`），拿到后 `show-location` + `moveToLocation` |
| 选点 | `wx.chooseLocation`，传入初始中心：行程已有坐标质心 → 目的地城市 → 我的位置 |
| 城市搜索 | 本地城市表（96 个城市，`utils/cities.js`），支持城市名/省份搜索，选中即切换选点地图起点；不接第三方地理编码（避免 Key 泄露与域名白名单） |
| 名称/地址 | 选点返回后名称与地址一起回填；用户手动改过则保留用户写法；坐标显示在页面上可核对 |

**两个环境限制（必须知道）**

1. 开发者工具里 `wx.chooseLocation` 点「确定」回传的是工具内置的固定模拟位置（实测 `30.2596, 120.1303`「浙江省杭州市」），与选点页实际位置无关，真机才正常。这类功能只能用真机验收。
2. 工具的 `moveToLocation` 不支持，模拟器里点「显示我的位置」地图不会动，真机正常。

**后台配置（已开通）**：`开发管理 → 接口设置` 开通 `wx.chooseLocation`；`设置 → 服务内容声明 → 用户隐私保护指引` 勾选位置信息。这两个没开，真机会直接走 fail 分支。

## 八、前端工程约定

1. **分层**：页面只写业务，接口全走 `services/`（`cloud.js` 统一 `call/run`，带 loading 与 toast，页面只处理成功分支）；纯函数放 `utils/`。
2. **WXML 里不做方法调用**：时长文本、日期文案、百分比宽度等一律在 JS 预计算。
3. **组件 props 只用单个小写单词**（`tabs`/`active`/`item`/`editing`），规避 WXML 属性名映射坑；组件 `styleIsolation: 'apply-shared'` 复用全局样式。
4. **日切换组件契约固定** `[{ index, label }]`，数组长度变化时 `activeDay` 必须夹取到合法范围（已加 `isFinite` 兜底）。
5. **样式 token**：主色 `#0f766e`，危险色 `#b91c1c`，正文 `#1f2328`，次要 `#6b7280`，弱 `#9aa1a9`，卡片圆角 20rpx，底部操作条留 `env(safe-area-inset-bottom)`。
6. **文案基调**：说人话、承认边界（例如「没有坐标也能保存，只是地图页看不到它」），不承诺做不到的事。
7. **云函数目录必须拍平**：函数根目录下不能有子目录或残留空目录，否则部署报 `EISDIR: illegal operation on a directory, read`。
8. **改完代码必须重启 IDE**：`cli.bat close --project` 再 `open --project`（或 Ctrl+B），只 `open` 可能仍在跑旧代码。

## 十一、已知限制与风险

| 风险 | 影响 | 处理建议 |
|---|---|---|
| 无分页、无增量同步 | 单行程 >300 点位/账目会被截断 | V1.5 加分页游标 |
| 冲突策略是整趟粒度 | 两人同时改不同地点也会互相冲突 | 现在会刷新重试；下一步可改为按点位版本号降低冲突面 |
| 成员没有昵称 | 列表里只能看到 openid 后四位 | V1.5 接入头像昵称（`chooseAvatar` / `nickname`）后再展示名字 |
| 单云函数 action 增长 | 体积/冷启动变慢 | 超过 20 个 action 时按域拆成 `api-trip` / `api-expense` |
| 无离线能力 | 山区无网不可用 | 后续做本地缓存 + 待同步队列 |
| 数据仅软删除、无导出 | 用户无法备份 | V1.5 加「导出行程为图片/文本」 |
| 地图与定位依赖网络与权限 | 未授权时功能降级 | 已做降级与引导，需真机复测 |
| 订阅消息字段名必须与模板一致 | 不一致时发送报 47003，日志可见但用户收不到 | 字段名集中在 `notify.js` 的 `FIELDS`；上线前实测一条 |
| 定时触发器依赖 config.json | 部署方式若忽略 config.json，触发器不会创建 | 部署后在控制台「云函数 → 触发器」确认 `dailyReminder` 存在 |
| 手帐照片无体积限制 | 云存储按量计费，大量原图会持续占空间 | 单行程 100 张上限，后续加体积与清理策略 |
| 删除照片只软删记录 | 云存储原图仍在 | 后续加「彻底清理」任务 |
| 结算不考虑“代付后对方已私下还钱” | 差额只是根据记账推算 | 文案已说明“只给建议”，后续可加标记已结清 |
